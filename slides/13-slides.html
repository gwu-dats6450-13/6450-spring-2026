Modern Infrastructure Tools

The Problem These Tools Solve

You’ve learned to process data at scale. But how do you ship, run, and manage that processing reliably in production?

Local notebook  →  "Works on my machine"  →  ??  →  Production

The gap between a working script and a running production system involves:

  • Reproducibility — same environment everywhere
  • Portability — runs on EC2, GKE, your laptop
  • Scalability — 1 container → 1,000 containers
  • Orchestration — who starts it? who restarts it when it crashes?
  • Eventing — what triggers the pipeline?

Docker, Kubernetes, Lambda, and Kafka each address a slice of this.

Docker

What is a Container?

A container packages your code together with its entire runtime environment: Python version, libraries, OS libraries, config.

Virtual Machine

  • Full OS per VM
  • Heavy (GBs)
  • Slow to start (minutes)
  • Strong isolation

Container

  • Shares host OS kernel
  • Lightweight (MBs)
  • Fast to start (seconds)
  • Process-level isolation

Note

Think of a container as a shipping container for software — standard shape, runs anywhere there’s a container runtime (Docker Engine, containerd).

Dockerfile: The Recipe

A Dockerfile describes how to build an image — a snapshot of the environment.

FROM python:3.11-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install -r requirements.txt

COPY pipeline.py .

CMD ["python", "pipeline.py"]
  • FROM — start from a base image
  • RUN — execute commands at build time
  • COPY — add files from your machine
  • CMD — what runs when the container starts

Images vs. Containers

Dockerfile  ──build──▶  Image  ──run──▶  Container
               (recipe)     (snapshot)     (running process)
  • An image is immutable — a versioned artifact you can push to a registry (Docker Hub, ECR)
  • A container is a running instance of an image
  • You can run many containers from the same image simultaneously
# Build the image
docker build -t my-pipeline:v1 .

# Run it
docker run my-pipeline:v1

# Push to AWS ECR
docker tag my-pipeline:v1 123456.dkr.ecr.us-east-1.amazonaws.com/my-pipeline:v1
docker push 123456.dkr.ecr.us-east-1.amazonaws.com/my-pipeline:v1

Docker Compose: Multi-Service Pipelines

Real pipelines often need multiple services. docker-compose.yml defines them together:

services:
  kafka:
    image: confluentinc/cp-kafka:7.6.0
    ports:
      - "9092:9092"

  spark-worker:
    image: bitnami/spark:3.5
    depends_on:
      - kafka

  pipeline:
    build: .
    depends_on:
      - kafka
      - spark-worker
docker compose up   # start everything
docker compose down # tear it all down

Tip

This is exactly how you’d set up a local development environment that mirrors production before pushing to the cloud.

Kubernetes

The Orchestration Problem

You have 50 containers running your data pipeline. Now what?

  • Which node do they run on?
  • What happens when one crashes?
  • How do you deploy a new version without downtime?
  • How do you scale up when load spikes?

Kubernetes (K8s) is a container orchestration system that answers all of these.

Key Concepts

Pod

  • Smallest deployable unit
  • One or more containers that share networking/storage
  • Ephemeral — can be rescheduled anywhere

Deployment

  • Declares desired state: “I want 3 replicas of this pod”
  • K8s ensures that state is maintained

Service

  • Stable network endpoint in front of pods
  • Load-balances across replicas
  • Decouples consumers from pod churn

Node / Cluster

  • Nodes are the machines (EC2 instances)
  • The cluster is the full collection managed by a control plane

Kubernetes in Data Engineering

You probably won’t manage K8s yourself — but you’ll encounter it:

Use case How K8s helps
Spark on K8s Spark driver + executors run as pods
Airflow on K8s Each task runs in an isolated pod (KubernetesPodOperator)
Model serving Scale inference pods up/down with traffic
Batch ETL jobs Kubernetes Jobs — run to completion, then clean up

Managed offerings remove the control-plane burden:

  • AWS EKS — Elastic Kubernetes Service
  • Google GKE — Google Kubernetes Engine
  • Azure AKS

Note

K8s depth is its own course. The key insight: it’s the runtime layer that makes containerized workloads production-grade.

AWS Lambda

Serverless: A Different Compute Model

With EC2, you provision a server and it runs 24/7 (whether or not you’re using it).

Lambda inverts this:

  • You upload a function (Python, Node, container image)
  • AWS runs it only when triggered
  • You pay per invocation + duration (millisecond billing)
  • No servers to manage, patch, or resize
def handler(event, context):
    # This runs when Lambda is triggered
    bucket = event['Records'][0]['s3']['bucket']['name']
    key    = event['Records'][0]['s3']['object']['key']
    process_new_file(bucket, key)
    return {"statusCode": 200}

Lambda Triggers

Lambda is event-driven — it responds to events from other AWS services:

S3 upload     ──────▶ Lambda ──▶ kick off Glue/Athena query
API Gateway   ──────▶ Lambda ──▶ lightweight REST endpoint
Kafka topic   ──────▶ Lambda ──▶ process each message
EventBridge   ──────▶ Lambda ──▶ scheduled batch jobs
DynamoDB      ──────▶ Lambda ──▶ react to row changes

This is the glue layer in modern data architectures — connecting events to actions without a long-running server.

Lambda Constraints

Lambda is not a universal replacement for EC2 or Spark:

Constraint Value
Max execution time 15 minutes
Max memory 10 GB
Ephemeral storage 10 GB (/tmp)
Concurrency Up to 1,000 simultaneous (default)
Cold start latency 100ms–1s (container images: higher)

Important

Lambda is the right tool for short, event-driven tasks — not for long-running Spark jobs or training large ML models. Know the boundary.

Apache Kafka

The Event Streaming Problem

Batch processing (Spark, Athena) assumes data has already arrived. But what about data arriving continuously?

  • Sensor readings every 100ms
  • Financial transactions in real time
  • Clickstream events from a web app
  • IoT device telemetry

You need a system that can:

  1. Ingest high-volume event streams reliably
  2. Buffer them so consumers can read at their own pace
  3. Replay events if a consumer falls behind or crashes

That’s Apache Kafka.

Kafka Core Concepts

Producer  ──writes──▶  Topic (partitioned log)  ──reads──▶  Consumer Group

Topic

  • Named, append-only log of events
  • Divided into partitions for parallelism
  • Events are retained for a configurable period (not deleted on read)

Producer

  • Any app that writes events to a topic

Consumer Group

  • One or more consumers reading from a topic
  • Each partition assigned to exactly one consumer in the group
  • Multiple groups can read the same topic independently

Broker

  • A Kafka server; a cluster has multiple brokers

Kafka vs. Spark Structured Streaming

These two work together, not in competition:

[Kafka Topic]
     ↓  (Spark reads Kafka as a streaming source)
[Spark Structured Streaming]
     ↓  (windowed aggregations, joins, ML scoring)
[S3 / Delta Lake / Iceberg]
     ↓
[Athena / downstream analytics]
Role Tool
Event ingestion & buffering Kafka
Stream processing & transformation Spark Structured Streaming
Durable storage S3 (Parquet/Iceberg)
Interactive analytics Athena

Note

You already know the Spark Structured Streaming layer from Week 11. Kafka is what feeds it in production.

Athena in the Streaming Ecosystem

Where Athena Fits

Recall from last week: Athena is serverless SQL on S3. It doesn’t replace streaming — it sits after it.

Real-time data
      ↓
[Kafka]          ← ingestion, buffering, replay
      ↓
[Spark Structured Streaming]   ← transform, enrich, aggregate
      ↓
[S3 — Parquet / Iceberg]       ← settled data in the lake
      ↓
[Glue Crawler updates catalog]
      ↓
[Athena]         ← ad-hoc SQL, BI tools, scheduled reports

Athena answers historical and analytical questions. Kafka answers right now.

Lambda as the Glue

Lambda connects the streaming and batch-query layers:

Pattern: S3 arrival → Athena

  1. Spark Structured Streaming writes Parquet to S3
  2. S3 event triggers Lambda
  3. Lambda calls boto3 to run MSCK REPAIR TABLE or CREATE PARTITION
  4. New data is immediately queryable in Athena
import boto3

def handler(event, context):
    athena = boto3.client('athena')
    athena.start_query_execution(
        QueryString="""
          MSCK REPAIR TABLE
          events_db.clickstream
        """,
        ResultConfiguration={
          'OutputLocation':
            's3://results-bucket/'
        }
    )

The Full Picture

Putting all five tools together:

[IoT / App / Logs]
       ↓
[Kafka Topic]  ←──── producers push events
       ↓
[Spark Structured Streaming]  ←── containerized on K8s or EMR
       ↓
[S3 — Iceberg tables]
       ↓  ← Lambda triggers catalog refresh
[Glue Data Catalog]
       ↓
[Athena]  ←── analysts query, dashboards refresh, Airflow schedules reports

Each tool is optional — swap in what you need. The pattern is: ingest → process → store → query.

When Would You Pick X Over Y?

These tools overlap — the key is understanding the tradeoffs.

Scenario Best Choice Why
10 GB CSV on your laptop Polars or DuckDB No cluster overhead
10 TB Parquet on S3, batch ETL Spark on EMR Distributed, fault-tolerant
10 TB on S3, ad-hoc SQL Athena No cluster to manage, pay-per-scan
Real-time events, <1s latency Kafka + Structured Streaming Streaming-native
Short event-triggered function Lambda Serverless, ms billing
Parallel Python workloads (not SQL) Ray Pythonic, flexible task graph
Repeatable scheduled pipeline Airflow DAG-based, retries, monitoring

Knowledge Check

Think-Pair-Share (1)

Question 1 — Storage & Query

You have 6 months of raw nginx access logs (~500 GB) sitting in S3 as gzipped text files. A product manager wants to run weekly aggregation reports.

Walk through the steps you’d take — what tools, what format, what query layer?

Key ideas to surface:

  • Convert to Parquet (Spark job or Glue) for columnar compression
  • Partition by date for scan efficiency
  • Register in Glue Catalog
  • Query with Athena — pay-per-scan, no cluster needed for reports
  • Schedule the conversion step in Airflow

Think-Pair-Share (2)

Question 2 — Scale & Tool Choice

Your daily Spark batch job processes 2 TB of transaction data and currently takes 6 hours. Your manager wants it under 1 hour.

What would you investigate first?

Key ideas to surface:

  • Partitioning strategy — are you reading more data than needed?
  • Shuffle-heavy operations (wide transformations) — can joins be avoided or broadcast?
  • Executor sizing — are workers underutilized (too few cores)?
  • Data format — CSV vs Parquet makes a 10x difference
  • Caching intermediate results if stages are reused

Think-Pair-Share (3)

Question 3 — Real-Time Architecture

A fintech startup wants fraud alerts within 2 seconds of a card transaction being processed. Describe a realistic architecture.

Key ideas to surface:

  • Kafka to ingest transactions as events
  • Spark Structured Streaming (or Flink) for windowed feature computation
  • ML model scoring inside the streaming job (Spark MLlib pipeline)
  • Lambda for alert dispatch (email / push) on high-score events
  • Athena for retrospective analysis of flagged transactions

Think-Pair-Share (4)

Question 4 — Tool Boundaries

A colleague says “we should just use Spark for everything — it handles batch, streaming, ML, and SQL.” What would you push back on, and when would you agree?

Key ideas to surface:

  • Agree: Spark is a strong general-purpose engine for large-scale data
  • Push back: cluster startup overhead makes it wrong for small data or short-lived tasks
  • Polars/DuckDB are faster for sub-100 GB single-machine work
  • Athena is cheaper for infrequent SQL queries on S3 (no cluster cost)
  • Lambda is right for lightweight event-triggered logic
  • The right tool depends on data size, latency, cost, and team familiarity

Think-Pair-Share (5)

Question 5 — Productionizing

You’ve trained a Spark MLlib model in a Jupyter notebook on your EC2 instance. How would you turn this into a production pipeline that retrains weekly on fresh S3 data?

Key ideas to surface:

  • Package the training script (not the notebook) — refactor to .py
  • Containerize with Docker for reproducibility
  • Store the model artifact back to S3 (MLlib’s model.save())
  • Orchestrate with Airflow: weekly DAG that pulls fresh data → trains → saves model
  • Deploy on EKS or as an EMR Step for the Spark compute
  • Monitor with CloudWatch; alert on training failures via Lambda + SNS
